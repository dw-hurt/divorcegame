# Contributing to Divorce Quest

First off, thank you for considering contributing to Divorce Quest! It's people like you that make this educational tool better for everyone.

## 🎯 Project Mission

Divorce Quest aims to provide an accessible, educational tool for people to explore divorce scenarios in a low-pressure, game-like environment. All contributions should align with this educational mission and maintain the highest ethical standards.

## 🤝 Code of Conduct

### Our Standards

- Be respectful and inclusive
- Focus on constructive feedback
- Respect privacy and confidentiality concerns
- Remember this tool affects people in difficult situations
- No legal advice - only educational information

## 🐛 Reporting Bugs

Before creating bug reports, please check existing issues. When creating a bug report, include:

- **Description:** Clear description of the problem
- **Steps to Reproduce:** Numbered steps to recreate the issue
- **Expected Behavior:** What should happen
- **Actual Behavior:** What actually happens
- **Browser/Environment:** Chrome 90, Windows 10, etc.
- **Screenshots:** If applicable

## 💡 Suggesting Enhancements

Enhancement suggestions are tracked as GitHub issues. When creating an enhancement suggestion, include:

- **Use Case:** Why is this enhancement needed?
- **Proposed Solution:** Your suggested approach
- **Alternatives:** Other approaches you've considered
- **Additional Context:** Screenshots, mockups, etc.

## 🔧 Contributing Code

### Getting Started

1. **Fork the repository**
   ```bash
   git clone https://github.com/dw-hurt/divorcegame.git
   cd divorcegame
   ```

2. **Create a branch**
   ```bash
   git checkout -b feature/your-feature-name
   # or
   git checkout -b fix/your-bug-fix
   ```

3. **Make your changes**
   - Write clear, commented code
   - Follow existing code style
   - Test your changes thoroughly

4. **Commit your changes**
   ```bash
   git add .
   git commit -m "feat: add new feature"
   # or
   git commit -m "fix: resolve issue with X"
   ```

5. **Push to your fork**
   ```bash
   git push origin feature/your-feature-name
   ```

6. **Open a Pull Request**
   - Describe what changes you made
   - Reference any related issues
   - Include screenshots if UI changes

### Commit Message Convention

We use conventional commits:

- `feat:` New feature
- `fix:` Bug fix
- `docs:` Documentation changes
- `style:` Code style changes (formatting, etc.)
- `refactor:` Code refactoring
- `test:` Adding tests
- `chore:` Maintenance tasks

Examples:
```
feat: add custody probability visualization
fix: resolve NaN error in income calculation
docs: update README with new API endpoints
```

### Code Style

#### JavaScript
- Use ES6 syntax where appropriate
- Use `const` and `let`, avoid `var`
- Use meaningful variable names
- Comment complex logic
- Keep functions small and focused
- Follow existing module pattern

#### CSS
- Follow BEM naming convention where appropriate
- Use CSS variables for colors
- Keep specificity low
- Mobile-first responsive design

#### HTML
- Semantic HTML5 elements
- Accessible markup (ARIA labels, alt text)
- Clear, descriptive IDs and classes

### Testing

Before submitting:

- [ ] Test in multiple browsers (Chrome, Firefox, Safari)
- [ ] Test on mobile devices
- [ ] Test with different scenarios
- [ ] Check browser console for errors
- [ ] Verify localStorage functionality
- [ ] Test idle timeout (if relevant)

You can help by contributing:

- Statistical averages

## 🔍 What We're Looking For

### High Priority
- Accessibility improvements (WCAG 2.1 AA)
- Mobile experience enhancements
- Additional state-specific data
- Improved Bayesian models
- Bug fixes
- Documentation improvements

### Medium Priority
- New question types
- UI/UX refinements
- Performance optimizations
- Additional language support
- Test coverage

### Nice to Have
- Advanced visualizations
- Export functionality
- Scenario comparison tools
- Additional game mechanics

## ❌ What We're Not Looking For

- Changes that provide legal advice
- Features requiring server-side processing
- External framework dependencies (stay vanilla JS)
- Features that compromise privacy
- Overly complex additions

## 📝 Pull Request Process

1. **Update documentation** if you've changed:
   - APIs or interfaces
   - Configuration options
   - User-facing features

2. **Add comments** explaining:
   - Complex algorithms
   - Non-obvious code
   - Assumptions made

3. **Test thoroughly**
   - Include test results in PR description
   - List browsers/devices tested

4. **Keep PRs focused**
   - One feature/fix per PR
   - Small, reviewable changes

5. **Be responsive**
   - Respond to review comments
   - Make requested changes
   - Be open to feedback
